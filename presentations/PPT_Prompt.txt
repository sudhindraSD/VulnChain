SLIDE 2 — THE PROBLEM: Software Supply Chain Under Attack
Left panel — "The Hidden Dependency Crisis":
• Modern software projects depend on hundreds of third-party libraries, each with their own dependencies (transitive dependencies)
• A typical React application contains 1,000+ packages in its node_modules directory — developers only explicitly install 20-30
• The remaining 97% are transitive dependencies that developers have zero visibility into
• A single vulnerability hidden 5 levels deep can compromise the entire application

Right panel — "Real-World Supply Chain Disasters":
• Log4Shell (CVE-2021-44228, 2021) — Critical vulnerability (CVSS 10.0) in a logging library used by millions of Java applications. Hidden 4-6 levels deep in most dependency trees. Cost: billions of dollars globally.
• XZ Utils Backdoor (2024) — Sophisticated nation-state supply chain attack embedded in a widely-used compression library. Attacker spent 2 years building trust before injecting a backdoor.
• SolarWinds (2020) — Nation-state attack via software supply chain affecting 18,000+ organizations including U.S. government agencies.
• event-stream (2018) — Malicious code injected into a popular npm library with 2 million weekly downloads, stealing cryptocurrency.

Bottom callout: "Current tools like Snyk and Dependabot flag known CVEs but fail to quantify how much risk a deeply nested transitive vulnerability actually poses to YOUR specific project."

SLIDE 7 — GNN DESIGN: Why Graph Neural Networks?
Left side — "Why Not Traditional ML?"
Dependencies naturally form a Directed Acyclic Graph (DAG). Traditional machine learning models like Random Forest cannot capture:
• Graph topology — the structure of connections between packages
• Message passing — how a vulnerability in node A propagates through nodes B and C to reach node D
• Variable-size input — every project has a uniquely structured dependency graph
Graph Neural Networks are architecturally designed for exactly this — they learn representations by aggregating information from neighboring nodes through iterative message passing.

Right side — "Why GAT Specifically?"
We selected Graph Attention Network (GAT) for three reasons:
(1) Attention weights reveal WHICH dependencies contribute most to a node's risk score — providing built-in explainability at no additional computational cost
(2) GAT handles directed graphs naturally, matching the directional nature of dependency relationships
(3) GAT is lightweight enough for CPU inference — no GPU required for deployment, enabling cost-effective real-time scanning

Show the model architecture as a vertical flow diagram:

Input Layer: 10-dimensional node feature vector per package → dim: 10
GAT Layer 1: GATConv(in=10, out=32, heads=4, dropout=0.3, concat=True) → dim: 128
ReLU Activation + Dropout Regularization (0.3)
GAT Layer 2: GATConv(in=128, out=32, heads=4, dropout=0.3, concat=True) → dim: 128
ReLU Activation + Dropout Regularization (0.3)
GAT Layer 3: GATConv(in=128, out=16, heads=2, dropout=0.2, concat=True) → dim: 32
ReLU Activation
Output Layer: Linear(32, 1) + Sigmoid Activation → dim: 1 (risk score 0.0–1.0)

Side panel — "The 10 Node Features":
1. cvss_max — Highest CVSS score among all CVEs for this package (range: 0–10)
2. cvss_avg — Mean CVSS score across all associated CVEs (range: 0–10)
3. cve_count — Total number of known CVEs affecting this package version (range: 0–N)
4. depth — Distance from root project node in the dependency tree (range: 0–N)
5. dependents_count — Number of packages within the project that depend on this node (range: 0–N)
6. downloads_monthly — Monthly download count from package registry as popularity signal (range: 0–N)
7. days_since_update — Days since last package update as maintainer activity indicator (range: 0–N)
8. is_dev_dependency — Binary flag indicating development-only dependency (0 or 1)
9. has_known_exploit — Binary flag for known active exploitation in the wild (0 or 1)
10. scope — Deployment scope weight: Runtime=1.0, Build=0.5, Test=0.2

SLIDE 9 — ATTENTION MECHANISM & EXPLAINABILITY
Title: "GAT Attention = Built-in Explainability"

How Attention Works:
For each pair of connected nodes (Package A depends on Package B), GAT computes a learned attention coefficient representing how much B should influence A's risk assessment. High attention weight means B strongly contributes to A's computed risk score. Low attention weight means B has negligible influence on A's risk profile.

Multi-Head Attention (4 independent heads per layer):
Each attention head learns to focus on different risk dimensions independently. The model combines 4 parallel perspectives for a richer, more robust risk assessment. This provides redundancy and captures multiple facets of vulnerability propagation simultaneously.

Why This Matters for Explainability:
Existing tools produce opaque results — "this package has CVE-XXXX." VulnChain produces transparent reasoning — "this package has a VulnChain Risk Score of 0.87 BECAUSE it receives 73% attention weight from vulnerable child package X (CVSS 9.8, runtime scope) and 20% from risky child package Y (CVSS 7.5, 3 dependents)." These attention-derived explanations are generated automatically as a byproduct of model inference.

SLIDE 10 — TRAINING STRATEGY: Cold Start Solution
Left — "The Cold Start Problem":
No ground-truth risk score dataset exists for software dependency vulnerabilities. Nobody has formally defined what the "correct" risk score should be for any given package in any given project context. Without labeled training data, supervised learning is impossible through conventional means.

Right — "Self-Supervised Learning with Heuristic Pseudo-Labels":
We generate training labels using domain-informed heuristic functions:
risk_label = (cvss_score / 10) × (0.85^depth) × scope_multiplier
• Packages with Critical CVEs (CVSS ≥ 9.0) in runtime dependencies receive labels 0.9–1.0
• High severity CVEs (CVSS 7.0–8.9) receive labels 0.7–0.8
• Development-only dependencies receive a 50% label reduction
• Depth decay factor (0.85^depth) progressively reduces labels for deeper dependencies

Bottom — "Training Configuration":
• Dataset: Top 500 open-source packages across npm, pip, and Maven ecosystems
• Scale: ~100,000 total nodes, ~250,000 total edges
• Split: 70% training / 15% validation / 15% test (graph-level split to prevent data leakage)
• Training time: ~30 minutes on CPU, ~5 minutes with GPU acceleration
• Inference latency: < 1 second per new repository scan

SLIDE 11 — BASELINE COMPARISON (Research Contribution)
Title: "VulnGAT vs 5 Baseline Methods"

Show a professional comparison table:

Method | Approach | Key Limitation
Raw CVSS Max | risk = max_cvss / 10 | Zero graph context; identical score regardless of topology
CVSS + Depth Decay | risk = (cvss/10) × 0.85^depth | Ignores transitive risk propagation paths
PageRank | NetworkX pagerank on dependency graph | Measures structural importance, not security risk
Weighted Sum | Hand-crafted weighted formula across 10 features | Weights are manually tuned, not learned from data
Random Forest | scikit-learn RF trained on same 10 node features | Treats each package independently; no message passing
VulnGAT (Ours) ★ | 3-layer GAT with attention-weighted message passing | Graph-aware, data-driven, inherently explainable

Evaluation Metrics:
• MSE (Mean Squared Error): Target < 0.05
• Pearson Correlation: Target > 0.85
• Spearman Rank Correlation: Target > 0.80
• Top-K Precision (K=10): Target > 80%
• Coverage of known vulnerable packages: Target > 90%

Key insight: "The performance gap between Random Forest and VulnGAT on deeply transitive vulnerabilities (depth 4+) represents the core research contribution — empirical evidence that graph structure provides measurable value for dependency risk assessment."
