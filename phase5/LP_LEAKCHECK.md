# LP Leak Check — 50% Masked-Edge Audit

Generated by `TrainModel/masked_edge_audit_leakfix.py` (new file). No existing script, result, or data file was modified or overwritten.

## 1. Which labels does LP use? — VERDICT: the leak is real

`TrainModel/masked_edge_audit.py::run_label_prop_baseline` (lines 373-443) takes two inputs:

- `data` = the **masked** `HeteroData` from `apply_edge_mask`. Its `hasVulnerability` edge_index has every edge of the masked packages removed, and `Package.x[:, 6]` is zeroed for those packages.
- `vpss_labels` = the **original** `phase4/vpss_labels_51repo.json`, loaded once in `phase5/part_c_masked_edge_multiseed.py` (line 64) and **never recomputed after masking**. `run_label_prop_baseline` builds `vpss_array` from this dict (lines 426-430).

Neighbourhoods come from the masked graph: undirected `dependsOn` Package<->Package edges (unchanged by the mask), plus Package<->Package links for packages sharing a **surviving** CVE. The score is the plain mean of `vpss_array[n]` over those neighbours (line 439); the no-neighbour fallback is the global mean of the original labels (line 432).

VPSS is a **closure** label. `data_pipeline/vpss_labeler.py` was verified bit-exact against the shipped label file on all 12,405 packages (0 field mismatches on `vpss`, `raw_sum`, `num_contributing_vulns`, `min_depth_to_vuln`):

```text
raw(P)  = sum_d [ sum CVSS(C) over (V,C) pairs at BFS depth d ] * 0.7^d * exposure(P)
vpss(P) = round(raw(P) / (raw(P) + 10), 6)
BFS goes outward through dependsOn (source = dependent, target = dependency)
```

**Therefore:** for a masked package P, its parents (packages that depend on P) still carry P's own CVE contribution in their VPSS at depth d, scaled by `0.7^d`. LP makes `dependsOn` undirected, so P's score is the mean of neighbour labels that include exactly the vulnerability the mask was supposed to hide. LP is partly reading the answer. The same applies to any ancestor of any masked package. `apply_edge_mask`'s dim-6 zeroing does not help: `run_label_prop_baseline` never reads `data['Package'].x`.

The suspicion is **not** wrong, so the audit proceeds.

## 2. LP_clean

`LP_clean` is the **same** `run_label_prop_baseline()` function, called on the **same** masked `HeteroData` (identical neighbour sets), but with VPSS labels recomputed from the masked graph:

1. `build_masked_graph()` removes every `hasVulnerability` edge whose source is a masked package. `dependsOn`, all node features, CVE nodes, and all other edges are untouched.
2. `data_pipeline/vpss_labeler.label_all()` recomputes VPSS for **all** 12,405 packages on that graph — same BFS, same `0.7^d` decay, same exposure tiers, same CVSS median-imputation, same `raw/(raw+10)` normalization, same 6-decimal rounding. Recomputing all packages (a superset of the neighbour nodes) is required because the official LP also uses the global mean over all labels for its no-neighbour fallback.
3. The official `run_label_prop_baseline()` is called with these labels. No new averaging code was written, so the only difference between `LP_original` and `LP_clean` is the label dictionary.

The original LP is kept untouched and reported side by side.

## 7. Where the code differs from the task description

These are reported rather than guessed around; everything below was kept exactly as the repository does it.

1. **Mask semantics.** `apply_edge_mask` does not remove 50% of `hasVulnerability` *edges*. It draws a Bernoulli(`mask_ratio`) per **eligible package** and removes **all** of that package's edges (plus a forced floor of 3 masked packages). So ~50% of eligible packages lose all their CVE edges; the number of edges removed is in the per-seed table above.
2. **The 5-seed 50% protocol** lives in `phase5/part_c_masked_edge_multiseed.py`, not in `TrainModel/masked_edge_audit.py::main` (which sweeps three ratios 0.10/0.30/0.50 with seeds 52/72/92). The hard N=645 / N=8,682 assertions come from `phase5/run_v22_sanity.py` lines 209-210. This script combines those three official pieces without changing them.
3. **`compute_own_vpss` unit mismatch (pre-existing).** It computes `own_raw = Σ CVSS/10` but divides by `raw_sum`, which the labeler stores as `Σ CVSS` (unscaled). `own_ratio` is therefore ~10x too small, so nothing passes 0.70 and `select_eligible_packages` takes its documented auto-relaxation to 0.30 — which is exactly what produces N=645 (confirmed in `phase5/preflight_v2_rerun.py:293`). Preserved verbatim.
4. **LP docstring vs code.** The docstring says 'connected by any edge type', but the code only uses Package<->Package `dependsOn` edges plus shared-CVE Package<->Package links; all cross-type edges are skipped. `idx_to_pkg_id` is an unused parameter. `LP_original` and `LP_clean` both go through this exact code path.
5. **BFS normalization.** `run_bfs_baseline` recomputes raw risk on the masked graph but divides by `max(raw_sum)` from the **original** label file instead of the labeler's `raw/(raw+10)`. That is a single positive constant scale factor, which cannot change a rank-based ROC-AUC; it was left untouched. BFS therefore uses the masked CVE set and does not inherit the LP label leak.
6. **Negatives are shared.** `never_vuln_indices` comes from the original labels for every method (including LP_clean), matching the official protocol and keeping the comparison fair. It is not recomputed on the masked graph.

## 8. What the numbers mean

`LP_original` = 0.719099 ± 0.006897; `LP_clean` = 0.632905 ± 0.007867; change = -0.086194. VulnGAT-HR = 0.631473 ± 0.004468; BFS = 0.528650 ± 0.003851.

The gap between `LP_original` and `LP_clean` is the part of the label-propagation baseline's score that came from unmasked closure labels — i.e. leaked information — as opposed to structure the masked graph genuinely supports (surviving shared-CVE links). Note that the pre-registered success bar in `phase5/part_c_masked_edge_multiseed.py` is `mean(LP_original) + max(0.02, 2*std(LP_original))`; this report does not recompute or re-adjudicate that gate, it only quantifies the leak.
